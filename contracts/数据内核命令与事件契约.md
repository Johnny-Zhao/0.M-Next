# 数据内核命令与事件正式契约 v1.1

- 状态:已采纳(v1.0 经对抗性审查修订为 v1.1,修订项见 §9,文中以 **[R-n]** 标注)
- 依据:《技术说明书》4.5~4.7(数据内核与核心数据表)、5.3(Remove/Delete/Unlink/Archive 语义)、6.11(数据内核工程契约:写入 P95≤500ms、禁止重任务进入事务链路)、7.14(事件驱动机制)、附录D.1/D.2;ADR-003/004/007
- 配套 Schema:`schemas/kernel-commands.schema.json`、`schemas/kernel-event-envelope.schema.json`(机器可校验,契约测试以此为准)

---

## 1. 总则

1. **唯一写入口**:所有主数据写操作必须经 `POST /workspaces/{workspaceId}/commands` 提交命令;视图、AI、规则引擎、制品适配器一律不得绕过命令层(D.1)。
2. **事务边界**:一条命令 = 一个数据库事务,事务内只做:权限前置检查 → 校验规则(实时轻量级)→ 主数据写入 → 版本记录写入 → event_outbox 写入。**禁止**在事务内调用 AI、全量检查、输出生成、深解析、仿真、HTTP 出站(6.11/8.11)。
3. **性能契约**:单命令写入 P95≤500ms。为守住该红线:单条 UpdateFields ≤100 个字段项;BatchCommand ≤200 个子命令且预估写行数 ≤2000,超限拒绝并引导走预览+冷路径任务 **[R-8]**。
4. **命令信封**(所有命令共用):

```json
{
  "commandId": "服务端生成 ULID,响应返回",
  "commandType": "CreateObject | ... (见 §2)",
  "workspaceId": "uuid,必填",
  "correlationId": "uuid,必填(D.2)",
  "idempotencyKey": "string(1..128),必填(见 §6)",
  "actor": "服务端从认证上下文注入,禁止客户端传入",
  "payload": { "按命令类型,见 Schema $defs" }
}
```

5. **响应统一结构**:`{ commandId, status: ACCEPTED|COMMITTED|REJECTED, idempotentReplay: bool, events: [eventId...], error?: {code, message, details, suggestion} }`。

## 3. 命令详规

通用前置(всех命令,逐条可测):
- P0 workspace 存在且状态可写,否则 `KERNEL-404-WORKSPACE-NOT-FOUND` / `KERNEL-410-WORKSPACE-ARCHIVED`;
- P1 actor 在该 workspace 具备对应 permission_code(权限矩阵),否则 `PERM-403-*`(权限错误统一 PERM- 前缀,本节只列内核码);
- P2 载荷过 JSON Schema,否则 `KERNEL-400-SCHEMA-INVALID`;
- P3 幂等检查(§6);
- P4 实时轻量规则(必填/格式/枚举,8.5),失败 `RULE-422-<规则名>`。

### 3.1 CreateObject

| 项 | 规定 |
|---|---|
| 载荷 | `objectTypeId, fields{fieldDefCode→value}, source{type: manual|import|rule|AI|artifact_sync|asset_reuse, ref?}, initialState?=DRAFT` |
| 幂等键 | 客户端生成 `ck-<uuid>`;导入/AI 场景用确定性键 `imp-<fileHash>-<rowNo>`、`ai-<changeSetId>-<itemNo>`,保证重试不重建 |
| 权限 | `object.create`(scope: workspace + objectType) |
| 校验 | objectTypeId 属于本空间模板版本且已发布,否则 `KERNEL-404-TYPE-NOT-FOUND`;fields 中的 code 均在 field_def 内,否则 `KERNEL-400-SCHEMA-INVALID`;必填字段满足(P4) |
| 事件 | ObjectCreated(after=对象摘要);每个非空初始字段一条 FieldChanged(before=null) |
| 错误码 | KERNEL-404-TYPE-NOT-FOUND、KERNEL-400-SCHEMA-INVALID、RULE-422-* |

### 3.2 UpdateFields

| 项 | 规定 |
|---|---|
| 载荷 | `objectId, expectedObjectVersion, fields[]: {fieldDefCode, value, expectedFieldVersion?}`(≤100 项) |
| 幂等键 | `ck-<uuid>`;自动保存场景按 (编辑会话, 防抖批次) 生成,重发不重复加版本 |
| 权限 | `field.update`(支持字段级 scope,字段级拒绝返回 PERM-403-FIELD-DENIED) |
| 校验 | 对象存在且非 VOID/FILED/DELETED,否则 `KERNEL-404-TARGET-NOT-FOUND`/`KERNEL-410-TARGET-ARCHIVED`;版本检测见 §5;字段被他人持锁 → `KERNEL-423-TARGET-LOCKED` |
| 事件 | 每个实际变化的字段一条 FieldChanged(携带 before/after/version,7.14"携带前后值与版本");汇总一条 ObjectUpdated;值未变化的字段项不产生事件 **[R-1]** |
| 错误码 | KERNEL-409-VERSION-CONFLICT、KERNEL-423-TARGET-LOCKED、KERNEL-410-TARGET-ARCHIVED、RULE-422-* |

### 3.3 ChangeState

| 项 | 规定 |
|---|---|
| 载荷 | `targetType: object|relation|fieldValue, targetId, fromState, toState, reason, expectedVersion` |
| 幂等键 | `ck-<uuid>` |
| 权限 | `state.change`(按 toState 分级:进入 CONFIRMED/FILED 需更高权限) |
| 校验 | 状态机(4.6):DRAFT→PENDING_CONFIRM→CONFIRMED→ISSUE→TO_FIX→FIXED→FILED;任意受控状态→VOID。fromState 必须等于当前态(双保险,与 expectedVersion 并用),否则 `KERNEL-409-STATE-TRANSITION-INVALID`;进入 CONFIRMED 前置规则检查未过 → RULE-422 阻断 |
| 事件 | StateChanged(before/after=状态) |
| 错误码 | KERNEL-409-STATE-TRANSITION-INVALID、KERNEL-409-VERSION-CONFLICT |

### 3.4 CreateRelation

| 项 | 规定 |
|---|---|
| 载荷 | `relationTypeId, sourceId, targetId, relationFields?, source{...}` |
| 幂等键 | `ck-<uuid>`;图形画线场景按 (viewSession, 线条临时ID) 确定性生成 |
| 权限 | `relation.create` + 对两端对象的可见权限(端点不可见按不存在处理,返回 KERNEL-422-ENDPOINT-INVALID,不泄露存在性)**[R-9]** |
| 校验 | 端点存在、属于本 workspace、状态非 VOID/DELETED,否则 `KERNEL-422-ENDPOINT-INVALID`;事务内对两端按 **id 升序加行锁**(防死锁/防与 Archive 竞态 **[R-5]**);类型/方向/端点类型匹配 relation_type 定义;同型同向同端点已存在活动关系 → `KERNEL-409-DUPLICATE-RELATION`(data_relation 防重唯一索引,4.7);基数超限 → `KERNEL-422-CARDINALITY-VIOLATION`;层级类关系成环 → `KERNEL-409-CYCLE-DETECTED`(闭包表同事务维护,ADR-004) |
| 事件 | RelationCreated |
| 错误码 | 上述 5 个 + KERNEL-404-TYPE-NOT-FOUND |

### 3.5 UpdateRelation

载荷 `relationId, fields, expectedVersion`;权限 `relation.update`;**端点变更(sourceId/targetId)按"Unlink+CreateRelation"语义整体校验**(重新查重、基数、环),事件为 RelationUpdated(before/after 含端点);其余同 3.2。错误码:KERNEL-409-VERSION-CONFLICT、KERNEL-409-DUPLICATE-RELATION、KERNEL-422-CARDINALITY-VIOLATION、KERNEL-409-CYCLE-DETECTED。

### 3.6 Archive(废止,保留历史)

| 项 | 规定 |
|---|---|
| 载荷 | `targetType: object|relation|artifact, targetId, reason, expectedVersion, relationPolicy: reject|unlink`(默认 reject)**[R-2]** |
| 幂等键 | `ck-<uuid>`;对已是 VOID 的目标重复执行返回幂等成功(状态不变、不发事件)**[R-2]** |
| 权限 | `archive.execute`;目标被正式输出快照引用时额外要求 `archive.referenced`(D.1"正式输出引用需提示影响") |
| 校验 | 目标为 object 且存在活动关系时:`relationPolicy=reject` → 返回 `KERNEL-422-ACTIVE-RELATIONS`(details 含关系清单前 50 条+总数);`relationPolicy=unlink` 且活动关系 ≤50 → 同事务逐条解除并发 RelationUnlinked;>50 → 拒绝并返回 `KERNEL-413-CASCADE-TOO-LARGE`,引导先走预览+批量任务(守住 P95≤500ms)**[R-2]** |
| 状态变化 | 任意受控状态 → VOID(已废止);历史版本、字段值、批注全部保留 |
| 事件 | Archived(+级联的 RelationUnlinked×n,同一 correlationId/causationId) |
| 错误码 | KERNEL-422-ACTIVE-RELATIONS、KERNEL-413-CASCADE-TOO-LARGE、KERNEL-409-VERSION-CONFLICT |

### 3.7 Unlink(解除关系)

| 项 | 规定 |
|---|---|
| 载荷 | `relationId`(或 `sourceId+targetId+relationTypeId` 三元组), `reason, expectedVersion, acknowledgeImpact?: bool` |
| 幂等键 | `ck-<uuid>`;重复解除已 UNLINKED 的关系幂等成功 |
| 权限 | `relation.unlink` |
| 校验 | 强语义关系(可触发生成,4.4)存在派生数据时:`acknowledgeImpact=false` → `KERNEL-422-DERIVED-DATA-IMPACT`(details 列派生对象);`=true` → 解除,派生数据**不删除**,由订阅方标记"来源已解除/过期" **[R-6]** |
| 状态变化 | 关系 status → UNLINKED(保留行与历史,非物理删除) |
| 事件 | RelationUnlinked(before 含端点与类型) |
| 错误码 | KERNEL-404-TARGET-NOT-FOUND、KERNEL-422-DERIVED-DATA-IMPACT、KERNEL-409-VERSION-CONFLICT |

### 3.8 SoftDelete(软删除)

| 项 | 规定 |
|---|---|
| 载荷 | `targetType: object|relation, targetId, reason, expectedVersion` |
| 权限 | 仅 DRAFT 状态目标的创建者或 `admin.softdelete`(D.1"仅限草稿或管理员受控场景");非草稿非管理员 → PERM-403 |

| 事件 | SoftDeleted |
| 错误码 | KERNEL-410-TARGET-DELETED(重复删幂等成功除外)、KERNEL-422-ACTIVE-RELATIONS |

| 项 | 规定 |
|---|---|
| 载荷 | `commands[]: 子命令(不含 BatchCommand,禁止嵌套), transactionMode: all_or_nothing|partial, previewId?` |
| 限额 | ≤200 子命令且预估写行 ≤2000,超限 `KERNEL-413-BATCH-TOO-LARGE` **[R-8]** |

## 5. 版本与并发

1. **版本字段**:data_object.version、data_field_value.version、data_relation.version 各自独立(4.6"字段值与关系可拥有独立状态");对象 version 在任何字段/状态变化时 +1,字段值 version 仅本字段变化时 +1。版本号只增不复用;历史版本不可变(4.6"正式数据不得覆盖即丢失")。
2. **乐观检测**:写命令必须携带 `expectedVersion`(UpdateFields 可另带字段级 `expectedFieldVersion`,精度更高、冲突更少)。检测在事务内 `UPDATE ... WHERE id=? AND version=?` 原子完成,影响行数=0 即冲突。
3. **冲突错误语义**(D.2 返回要求):

```json
{ "code": "KERNEL-409-VERSION-CONFLICT",
  "message": "对象已被他人修改",
  "details": { "targetType":"object", "targetId":"…",
    "expectedVersion": 7, "currentVersion": 9,
    "conflictingFields": [ {"fieldDefCode":"cost","yourValue":…,"currentValue":…,"changedBy":"…","changedAt":"…"} ] },
  "suggestion": "拉取最新版本对比合并后重试;无重叠字段可直接以字段级版本重提" }
```

4. **字段级合并规则 [R-1]**:UpdateFields 同时带对象级与字段级版本时,以字段级为准——其他字段被他人修改不阻塞本次提交(对象 version 仍 +1),仅当**同一字段**版本冲突才返回 409。这使"两人并发改同一对象的不同字段"无冲突,符合 9.x 协同要求(字段级锁、乐观并发)。
5. **5.3 四种操作 → 命令与状态映射**:

| 5.3 操作 | 语义 | 命令 | 状态变化 | 事件 |
|---|---|---|---|---|
| Remove | 从当前视图移除 | **非内核命令**(视图服务删 view_element) | 主数据无变化 | 无主数据事件 |
| Delete | 删除底层对象或关系(软) | SoftDelete | → DELETED(终态,默认不可见,保留审计) | SoftDeleted |
| Unlink | 解除关系 | Unlink | 关系 → UNLINKED(保留历史) | RelationUnlinked |
| Archive | 废止但保留历史 | Archive | 任意受控状态 → VOID(已废止) | Archived |

注:4.6 生命周期终态"已归档(FILED)"经 `ChangeState` 达成(正常归档),与 Archive 命令的"废止(VOID)"是两个不同状态,禁止混用。

## 6. 幂等键设计

- 唯一性约束:`command_log(workspace_id, idempotency_key)` 唯一索引;command_log 记录 `commandId, commandType, payloadHash(SHA-256), resultSnapshot, decidedAt`。
- 重放判定:同键且 payloadHash 相同 → 返回首次结果,`idempotentReplay=true`,**不重复执行、不重复发事件**;同键但 payloadHash 不同 → `KERNEL-409-IDEMPOTENCY-CONFLICT`。
- 保留期:90 天(覆盖离线/断网恢复重放窗口,9.1.5),到期归档。
- 确定性键约定:导入 `imp-<fileHash>-<row>`、AI 确认 `ai-confirm-<changeSetId>`、批量子项 `<批次键>#<index>`——保证跨进程重试天然幂等。

## 7. Outbox 投递语义(ADR-007)

1. **事务内写入**:命令事务内向 event_outbox 插入事件行(id=eventId, event_type, aggregate_type, aggregate_id, payload=完整信封, status=PENDING, retry_count=0, created_at)。主数据成功而事件丢失、或事件发出而主数据回滚,均不可能发生(同事务原子)。
2. **投递器**:轮询发布器以 `FOR UPDATE SKIP LOCKED` 取 PENDING 批次(≤500 行/批,按 created_at 序)→ 按 `hash(aggregate_id)` 路由发布至 RabbitMQ(一致性哈希交换器,保证同聚合顺序)→ broker confirm 后置 PUBLISHED 并记 published_at;失败 retry_count+1,指数退避;retry_count>10 → status=QUARANTINED + 告警,人工处置。LISTEN/NOTIFY 仅用于唤醒、降低延迟。
3. **至少一次**:投递器在"已发出、未标记"窗口崩溃会造成重复投递——这是契约的一部分,**订阅方必须幂等**。
4. **订阅方幂等要求**(强制,所有订阅方准入条件):处理前查 `consumer_dedup(consumer_group, event_id)`,已存在则 ACK 跳过;处理与去重记录写入同一本地事务;按信封 `sequence` 检测同聚合乱序,乱序事件延迟重投(NACK+requeue)而非按错序处理 **[R-10]**;消费失败进各消费组死信队列,不阻塞其他聚合。
5. **顺序承诺范围**:仅承诺**同一 aggregate_id 内**按 sequence 有序;跨聚合、跨事件类不承诺全局顺序,订阅方不得依赖。
6. **清理**:PUBLISHED 行按天分区,保留 14 天后归档删除(审计依赖 audit_log 而非 outbox)。

## 9. 对抗性审查(12 个边界场景,逐个裁决;发现缺口已修订入正文)

| # | 场景 | 契约如何处理 | 审查结论 |
|---|---|---|---|
| 1 | **两用户并发修改同一字段**:A、B 同时基于 v7 改 cost | 字段级 expectedFieldVersion:先提交者成功 v8;后提交者 `KERNEL-409-VERSION-CONFLICT`,details 给出 yourValue/currentValue/changedBy,前端展示差异合并 | 通过(§5.2/5.3) |
| 2 | **并发修改同对象不同字段**:A 改 cost,B 改 owner | v1.0 仅有对象级版本 → B 必然假冲突。**缺口 → 修订 [R-1]**:引入字段级版本判定,对象版本仍递增但不作为阻塞条件 | 已修订(§5.4) |
| 3 | **废止有活动关系的对象** | v1.0 未定义级联。**缺口 → 修订 [R-2]**:relationPolicy=reject(默认,返回 KERNEL-422-ACTIVE-RELATIONS 及清单)/unlink(≤50 同事务级联);>50 拒绝(KERNEL-413-CASCADE-TOO-LARGE)引导冷路径批量任务,守住 P95≤500ms 与"禁止重任务进事务"(6.11) | 已修订(§3.6) |
| 4 | **批量命令部分失败**:partial 模式第 37 项规则失败 | 子命令独立事务:1–36、38–N 已提交并发事件;37 记入 results[](含错误码);重试以子键 `<批次键>#37` 只补该项,不重放已成功项。all_or_nothing 模式则整体回滚且零事件。**缺口 → 修订 [R-3]**:v1.0 未定义子键,重试会整批重放 | 已修订(§3.9) |
| 5 | **确认已过期的 AI 变更集**:确认时目标对象已被人改过 | 过期=超时 **或** baseVersion 漂移;命中即 `AI-409-CHANGESET-EXPIRED`,且逐项预检兜底(漂移只发生在个别项时返回 AI-422-ITEM-PRECHECK-FAILED 列明失败项,用户剔除后重提)。**缺口 → 修订 [R-4]**:v1.0 只有超时判定,无基线漂移判定 | 已修订(§3.10) |
| 6 | **CreateRelation 与 Archive 端点对象竞态**:画线同时对方废止对象 | 两命令都对目标行加锁(关系命令按端点 id 升序锁,Archive 锁目标行):串行化后,后执行者看到 VOID → `KERNEL-422-ENDPOINT-INVALID`/`KERNEL-410`。**缺口 → 修订 [R-5]**:明确锁顺序,排除 AB-BA 死锁 | 已修订(§3.4) |
| 7 | **用户在表格删行,本意是 Remove 却被实现为 Delete** | 契约层面显式声明 Remove 非内核命令、SoftDelete 权限仅限草稿创建者/管理员——视图层删行默认映射 Remove,想真删会因 PERM-403 被挡。**缺口 → 修订 [R-7]**:v1.0 未显式排除 Remove | 已修订(§2) |
| 8 | **巨型批量(导入 5 万行)走 BatchCommand 打爆热路径** | 限额 ≤200 子命令/≤2000 写行,超限 `KERNEL-413-BATCH-TOO-LARGE`,引导"预览(commands:preview)→ task_queue 冷路径导入任务(任务内部分片为多个合规批次)"。**缺口 → 修订 [R-8]**:v1.0 无限额 | 已修订(§1.3/§3.9) |
| 9 | **越权探测**:对无权可见对象发 CreateRelation 试探其存在 | 端点不可见与不存在统一返回 `KERNEL-422-ENDPOINT-INVALID`,不区分语义,不泄露存在性。**缺口 → 修订 [R-9]** | 已修订(§3.4) |
| 10 | **重复投递+乱序**:Outbox 重发且 FieldChanged v9 先于 v8 到达 | 重复:consumer_dedup 按 eventId 去重。乱序:同聚合经哈希路由理论有序,但重投/重平衡可破坏。**缺口 → 修订 [R-10]**:信封增加 sequence,订阅方乱序时 NACK 延迟重投 | 已修订(§4.1/§7.4) |
| 11 | **幂等键被复用于不同载荷**(客户端 bug) | payloadHash 比对 → `KERNEL-409-IDEMPOTENCY-CONFLICT`,返回原 commandId 供排查;绝不静默执行第二种载荷 | 通过(§6) |
| 12 | **强语义关系解除后派生数据悬空**(矩阵勾选生成的追溯对象) | acknowledgeImpact 两段式:未确认 → KERNEL-422-DERIVED-DATA-IMPACT 列派生清单;确认后解除,派生数据由规则/生成服务订阅 RelationUnlinked 标记"来源已解除",不在事务内级联删除(守住事务边界)。**缺口 → 修订 [R-6]** | 已修订(§3.7) |

审查结论:12 个场景中 9 个暴露 v1.0 缺口,已全部以 [R-1]~[R-10] 修订并回写正文与 Schema;无遗留缺口。后续新增场景按 ADR 变更流程演进本契约(schemaVersion 字段保证信封可演进)。

## 10. V3.3 标准契约对齐附录

### 10.1 事件信封与 CloudEvents 1.0 语义映射

本契约事件信封与 CloudEvents 1.0 **语义对齐(B 级)**。内部信封 v1 保持现有字段名与 `schemaVersion=1`,不改 Schema;如外部网关需要 CloudEvents 格式,由适配层进行转换,不得要求内核事件生产者直接依赖 CloudEvents SDK。

| CloudEvents 1.0 属性 | 内部信封字段/转换规则 | 约束 |
| --- | --- | --- |
| `id` | `eventId` | 一一映射,保持全局唯一与订阅方幂等语义。 |
| `source` | 由 `workspaceId` 与 `targetType/targetId` 组成稳定 URI | 适配层生成,不得使用临时主机名或公网地址。 |
| `type` | `eventType` | 一一映射到注册的 canonical eventType。 |
| `specversion` | 对外适配层固定输出 `1.0`;内部 `schemaVersion` 表达信封/数据契约版本的对应语义 | 两者不是数值直拷贝;内部 v1 不改字段。 |
| `time` | `occurredAt` | 一一映射,RFC3339。 |

其余内部字段作为 CloudEvents `data` 内容或扩展属性映射。适配层必须保留 `workspaceId`、`targetType`、`targetId`、`version`、`before`、`after`、`actor`、`source`、`correlationId`、`causationId` 与 `sequence`,不得因格式转换丢失因果链、版本或审计语义。

### 10.2 AsyncAPI 通道命名约定

- 工作空间事件通道统一命名为 `workspace.{id}.events`,`{id}` 为 `workspaceId`。
- 通道消息必须引用本契约事件信封 Schema,并声明至少一次投递、同聚合顺序范围、订阅方幂等与死信处理语义。
- 事件类型、订阅方和消息通道应可生成 AsyncAPI 文档;文档发布与对外网关转换属于实现期任务,本附录不实现消息转换代码。

### 10.3 OpenAPI 3.1 生成约定

- 命令端点 `POST /workspaces/{workspaceId}/commands`、查询端点、分页过滤、错误响应与错误码必须可生成 OpenAPI 3.1 机器可读文档。
- 实现期由代码注解或等价单一来源生成 OpenAPI,不得手工维护与实现脱节的第二份接口事实源。
- CI 契约测试必须校验生成的 OpenAPI 与命令/响应 JSON Schema、错误响应结构及版本兼容策略一致。

### 10.4 对齐边界

本附录只增加标准语义映射与实现期生成约定。它**不修改**事件信封字段、`schemaVersion`、命令端点、错误码或配套 JSON Schema,也不代表已实现 CloudEvents 网关转换、AsyncAPI 文档发布或 OpenAPI 生成能力。

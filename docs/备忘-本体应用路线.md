## 三层路线

### 第一层 — 领域本体 = profile 库纪律【随 v0.1 顺路,零平台代码】

把每份 profile manifest 当领域本体治理:概念定义有出处(标准/规范条款)、版本化、`extends` 只增不改、复用先于新建。
**v0.1 卡C 即第一份领域本体**:给 module 定义 `power_w` 与总功耗派生、超预算规则,就是本体条目(概念+公理)。不新增任何机制。

### 第二层 — 顶层本体 = 一份 core base profile【v0.1 发布后,预算 1 天】

抽 `core` profile(artifact / requirement / parameter / interface / rationale 一类跨域概念),各领域 profile extends 之。机制现成(泛化 + extends),工作量是设计而非开发。
**硬边界(防时间黑洞)**:≤10 个概念;一页纸;只收录已有三个域(室内/技术方案/MBSE)的公共部分;不引 BFO/DOLCE/UFO 之争;超出即砍。

### 第三层 — 语义互操作(RDF/OWL/SHACL)【BL-07,按需触发】

走现成交换适配器 SPI 出 JSON-LD/Turtle 导出,不动内核。
**触发条件(满足其一才启动)**:① 有真实用户要求对接知识图谱/语义库;② 有付费级需求要求 OWL 推理或 SHACL 校验。触发前保持 backlog 状态。

## 禁止事项

1. v0.1 期间不做任何本层面工作(第一层随卡C 顺路除外);
2. 不引入 RDF 三元组存储、reasoner、SPARQL 端点;
3. 顶层本体不超预算(1 天/一页/≤10 概念);
4. 不以"本体完整性"为由给 profile 机制加功能——现有机制不够用时,先写触发证据再议。

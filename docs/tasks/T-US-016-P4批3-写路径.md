## 背景与关键决策(必读)

**架构现状(务必先读代码再动手):**
同源当前有两条完全独立的写路径,`T-US-014/015` 只搭了「装载期」的 gateway 抽象,**没有**把 UI 写接到 gateway:

- **Mock 模式(线上默认):** 各视图组件直接调用**单例** `workspaceStore`(`state/workspace-store.ts` 末尾 `export const workspaceStore = new WorkspaceStore()`)的同步写方法(如 `canvas-view.tsx` 的 `workspaceStore.createRelation(...)`、`workspaceStore.deleteObject(...)`,`inspector-versions-panel.tsx`/`matrix-board.tsx` 的 `workspaceStore.undo(...)`),或经 `sessionStore.requestWrite(...)` 的 RBAC 闸(直写 `updateField` 或转本地 changeset)。`boot.tsx` 在 Mock 模式**不实例化任何 gateway**。`MockUnisourceGateway` 仅存在于测试/装载抽象,线上 UI 不碰它。
- **Kernel 模式(`?backend=1&ws=`):** `boot.tsx` 建 `KernelGateway`,`loadWorkspace()`→`DemoSeed`→`applyDemoSeed` 把内核数据灌进同一个单例 `workspaceStore`(此后 objects/relations 的 `id` 已是内核 UUID,由 `identity-remap` 重写表达层引用),随后 UI 的写**仍走本地单例 store**,`KernelGateway` 的写面全部 `throw new Error("T-US-016")`,永不被调用。顶栏 ribbon 显示 `KERNEL · {ws} · 写入本地`(`shell/workspace-header.tsx:81`)。

**所以本卡的实质工作:在 kernel 模式下,把单例 store 的数据写「顺带」下发内核命令,并保留 Mock 模式零回归。** 采用用户已拍板的**乐观本地写**策略。

**决策 1 — 乐观本地写 + 后台内核命令 + 失败回滚(async 桥接策略,已拍板)。**
UI 调用 → 本地 store 同步应用(即时刷新,= 现 Mock 行为)→ 后台 fire-and-forget 下发内核命令(用刚写前的本地版本号做乐观锁)→ 成功不动本地;失败回滚该次改动并 Toast。理由:① 保 Mock 零回归(本地写就是 Mock 行为);② 保 store 同步公开 API(红线7:async 化是本卡显式课题,但此策略下 UI 写仍同步返回,只有命令派发异步);③ 保演示即时手感(招牌流「王芸确认 ¥1,199 同步 3 文档」是内联 `updateField`,最忌延迟);④ 409 冲突有干净回滚点。淘汰的 pending 态方案会改 UX、把 pending 穿透进各视图组件、伤手感。

**决策 2 — 以「写汇 WriteSink」注入单例 store,不改调用点。**
给单例 `workspaceStore` 加一个可选写汇(`WriteSink`),默认 `null`。四个**数据轨**写方法(`updateField`/`createObject`/`createRelation`/`deleteObject`)在本地应用后 **fire-and-forget** 通知 sink;`undo` 复用 `updateField` 天然进 sink(见决策 5)。**Mock 模式不注入 sink = 纯本地 = 既有测试与调用点零改动**。这是最小爆炸半径,且正是交接文档所述「store 写方法接 gateway」。调用点(grid/doc/canvas/matrix/…)一律不改。

**决策 3 — actor 随 RoleSwitcher(废硬编码)。**
`boot.tsx:53` 现把 `"wangyun"` 硬编码进 `KernelGateway` 构造。本卡让 bridge 每次派发前读 `sessionStore.getSnapshot().currentMemberId`,解析为 actorId 后 `gateway.setActor(actorId)`(内核侧 `CommandClient.setActorId`→`X-Actor-Id`)。E3 §三:`session(RoleSwitcher) → X-Actor-Id + CommandClient.setActorId` **直映**。member→actorId 用**演示级 identity 直传**(真实身份解析属 G2/017,单独一处映射函数标注),构造里的 `"wangyun"` 降为初值、运行时被 bridge 覆盖。

**决策 4 — 仅对象版本乐观锁,省略字段版本。**
`updateFields` 命令支持双乐观锁(`expectedObjectVersion` + 可选 `expectedFieldVersion`)。本卡**只传 `expectedObjectVersion`**(= 写前本地对象版本),`expectedFieldVersion` 省略。理由:G8——内核 ViewObject 暂无字段级 version,本地 `fieldVersion` 是 Mock 合成值,传进去必假冲突;`FieldUpdate` 契约注释明示「省略/置 null = 仅按对象版本锁」。

**决策 5 — G10 撤销 = 读反向值 + 新 UpdateFields,每次重读版本。**
`store.undo(eventId)` 对数据字段 inverse 已经走 `this.updateField(inverse.objectId, inverse.fieldCode, inverse.value, …)`,而 `updateField` 取 `current.version`(即写时重读)。因此 undo 天然经 sink 下发一条反向 `UpdateFields`、且每次重读版本——**无需为 undo 单独接线**。视图/KPI 的 undo 走 `updateViewConfig`/`setKpiVisible`(前端投影,不进 sink),正确地不下发命令。E3 §四 G10 口径达成。

**决策 6 — 创建路径的内核 id 回填(本卡最大风险点,审查重点)。**
`CreateObject`/`CreateRelation` 命令返回 `CommandAck`(commandId/events),**不直接回传新实体 id/version**。本地 `createObject` 生成临时 id(`obj-<typeCode>-<seq>`),内核分配 UUID,二者须对齐。方案:gateway 在命令成功后按**业务键**(`objectTypeCode + name`,复用 `identity-remap.objectBusinessKey`)重读 read-model 认领内核对象(id+version),bridge 调 store 的回填方法把本地临时 id 换成内核 id,**连带**改写 relations 端点、fieldRefs.objectId、canvas view config 节点的 objectId(三者均在 workspace 状态内,回填不外溢)。demo seed 内 name 唯一,业务键确定性成立。审查须重点核这条链;若认领不到,回滚该临时对象并 Toast。**范围注:** `selection-store` 的选中项 remap 不在本卡内(选中一个刚建对象的临时 id 属边角场景,下次选择/重载即自愈),故封闭清单不含 selection-store。

**决策 7 — 错误映射,守边界。**
`CommandFailure` 在 `@m-next/views`。`kernel-gateway.ts`(运行时 import 白名单内)捕获 `CommandFailure`→经 `dto-mappers.ts`(type-only import `CommandError`/`ConflictField`)的 `mapCommandError` 映射成 unisource 本地 `WriteRejection`→抛给 bridge;**bridge 零 `@m-next/views` import**。`@m-next/views` 根桶 `index.tsx:11` 已 `export *` command-client,`CommandFailure`/`CommandError`/`ConflictField` 均可直接取。

**决策 8 — 冲突 UI(乐观锁冲突提示)。**
bridge 捕获 `WriteRejection`→`pushToast`(既有 `primitives/toast`,复制 views `conflict/conflict-dialog` 的体验而**不 import**):标题取错误标题(如「乐观版本冲突」),desc 列 `conflictingFields` 明细(字段 / 当前值 / 改动人 / 时间),并本地回滚。可选加一个「重载」动作走 `configureBackendReload`。错误码文案对齐 `command-client.ts` 的 `errorTitles`(409/410/423/422/PERM-403)。

**决策 9 — ribbon 翻牌。**
`shell/workspace-header.tsx` 的 `KERNEL · {ws} · 写入本地` → `内核直写`(写入已下发内核)。仅文案;如需变色则 `us-components.css` 追加式改。

**范围裁剪(明确排除,写清理由):**
- **`updateRelationField` 留本地:** `CommandClient` **无** `UpdateRelation` 方法,而 views 不可动。故 kernel 模式下关系字段写仍仅本地,记为缺口(未来 views 卡补 `updateRelation` client 方法后再接)。
- **前端投影写留本地:** `bindSlot`/`unbindSlot`(G5)、`addFieldRef`/`rebindFieldRef`(G7)、`updateViewConfig`/`setKpiVisible`(G6)、`setPluginState`(注册表)、`addReviewRecord`(G2/G8)、`addRelationComment`/`addActivity` —— kernel 模式**不派发命令**(其 store 方法不通知 sink),文档记对应 G 缺口。
- **陈默越权→审批(PENDING_CONFIRM + ChangeState)属 017/G2:** 本卡 `createObject` 走默认 **DRAFT** 直创(不带 `initialState`);Mock 现有 `sessionStore.requestWrite` 越权转本地 changeset 的路径在 backend 模式**仍走本地**,直至 017 接 G2 权限投影(四人→ADMIN/AUTHOR/AUTHOR/VIEWER)与 `ChangeState`。理由:审批链会拖入权限投影与状态机命令,是 017 的明确课题;本卡专注数据写 happy-path + 冲突。**⚠️ 此处对交接文档 §七.2 关于 016 曾提「CreateObject 陈默审批链改走 PENDING_CONFIRM」的试探性描述做了收窄,审查时请确认此裁剪。**

## 行为要求(逐条可测)

1. **Mock 零回归:** 未注入 sink 时,四个写方法与 `undo` 行为逐位同前;既有 `workspace-store`/`mock-gateway`/各视图测试**零改动**通过。
2. **updateField(kernel):** 本地应用后下发 `UpdateFields{objectId, expectedObjectVersion=写前对象版本, fields:[{fieldDefCode, value}]}`(省略 `expectedFieldVersion`);成功不改本地。
3. **冲突回滚:** `UpdateFields` 收 `KERNEL-409-VERSION-CONFLICT`→bridge 将该字段回滚为前值(store 静默)、`pushToast`(标题「乐观版本冲突」;desc 列 `conflictingFields`:字段 / 当前值 / 改动人)、可选「重载」动作。`423`/`422`/`PERM-403` 同样回滚 + 对应文案。
4. **actor:** bridge 每次派发前按当前 `sessionStore.currentMemberId` 解析 actorId 并 `setActor`;切角色后写入携带新 `X-Actor-Id`(测试断言)。
5. **deleteObject(kernel):** 下发 `Archive{targetType:"object", targetId, expectedVersion=删前版本}`(`relationPolicy:"unlink"` 由 client 内置);失败恢复对象及其关系(store 静默回填)。
6. **createObject(kernel):** 解析 `objectTypeCode`→`typeId`(缓存)→`CreateObject{objectTypeId, fields}`(**不带** `initialState`)→命令后按业务键重读认领内核 id+version→store 回填临时 id(连带 relations 端点 / fieldRefs / canvas 节点,均在 workspace 状态内);失败移除临时对象。
7. **createRelation(kernel):** 解析 `relationTypeCode`→`id`→`CreateRelation`→认领内核 `relationId`→回填;失败移除临时关系。
8. **undo(kernel,G10):** 数据字段 undo 经 `store.undo`→`updateField(inverse)`→sink→`UpdateFields`(反向值,`expectedObjectVersion` 重读);视图/KPI undo 不派发(前端投影)。
9. **串行化:** 同一 `objectId` 的多次写按 FIFO 派发,避免版本竞态。
10. **fire-and-forget:** store 写方法**同步返回、绝不因内核失败抛错**;失败只经 Toast + 回滚异步呈现。
11. **ribbon:** backend 模式顶栏显示「内核直写」。
12. **前端投影写在 kernel 模式仍仅本地:** 不产生内核命令(测试断言 sink 未被调用 / 命令未发)。

# 附件存储 — 设计稿(待人确认后才发实现卡)

> 状态:**设计征求**。本稿提出 blob 后端、数据模型、上传/关联路径、契约新增项。其中**契约新增(命令/端点/读视图/迁移)属 AG-301/501 人发起改动**——本稿即发起,需你逐项拍板后才开实现卡。先定边界,再写代码。

## 1. 为什么要它 / 边界在哪

比选要传报价单、方案 PDF、资质证明;能源/室内要挂引用图纸、外部工具产物。这些是**被引用的工件(artifact),不是平台建模/计算的实体**——与 hub 定位一致:几何/外部产物**引用不内建**。所以附件**不进元模型**(不做成 object_type/field),而是**对象的旁挂物**:一个对象(或对象的某个评分项)可以挂 0..N 个附件,平台只负责**存、取、关联、留痕**,不解析内容。

非目标(本期不做):在线预览渲染、版本树、全文检索、富权限矩阵、跨工作空间共享、CDN 直传。

## 2. 关键决策(每条给推荐 + 备选,待你确认)

### D1 blob 落在哪 —— 推荐:`StorageBackend` SPI + 文件系统默认实现
- **推荐**:定义 `engines`(或 `shared`)里一个 `StorageBackend` 接口(`put(key, stream, meta)` / `get(key)` / `delete(key)` / `stat(key)`),**默认实现写本地文件系统**(配置根目录,如 `MNEXT_STORAGE_DIR`),key = 内容寻址 `sha256` 前缀分桶。**S3/MinIO 等留作后续实现挂同一 SPI**,零改上层。
- 备选:① 直接存 Postgres `bytea`/大对象——简单但库膨胀、备份痛,否。② 直接写死本地路径无 SPI——以后换云存储要改上层,否。
- **理由**:与平台"一切外部能力走 SPI"一致;dev/CI 用文件系统零依赖(不需 MinIO 容器),生产可换。

### D2 元数据放哪 —— 推荐:专用 `attachment` 表 + 读模型投影
- 新迁移(`V15__attachment.sql`)建表 `attachment`:
  `id(uuid pk)`、`workspace_id`、`object_id(nullable)`、`scope_ref(nullable, 文本——指向具体评分项/字段,如 "score:<criteriaCode>")`、`filename`、`content_type`、`size_bytes`、`sha256`、`storage_key`、`status(ACTIVE/DELETED)`、`created_by`、`created_at`。
- 走 CQRS:命令写主表 + `event_outbox` → 投影到 `rm_attachment` 供 `/views` 只读查询(与现有读写分离一致)。
- 备选:把附件做成一等 object_type——**否**,污染元模型、且附件不该参与派生/规则/联邦。

### D3 写路径 —— 推荐:两步(先传 blob,再下 `AttachFile` 命令)
命令总线保持**纯 JSON、无二进制**(AG-110 写经命令,但不把 MB 级字节塞进命令日志):
1. `POST /workspaces/{wid}/attachments/blob`(multipart 或 octet-stream)→ 服务端校验大小/类型 → 经 `StorageBackend.put` 落 blob → 返回 `{storageKey, sha256, sizeBytes, contentType}`。**此步只落 blob,不写主数据、不建 attachment 行**(幂等:同 sha256 复用 key)。
2. `AttachFile` 命令(JSON):`{workspaceId, objectId?, scopeRef?, filename, contentType, sizeBytes, sha256, storageKey}` → 校验 storageKey 存在且 sha256/size 一致 → 写 `attachment` 行 + outbox 事件 → 投影。
- **下载**:`GET /workspaces/{wid}/attachments/{id}/content` → 查元数据 → `StorageBackend.get` 流式回传(校验 workspace 归属)。
- **列表**:`GET /workspaces/{wid}/views/attachments?objectId=&scopeRef=`(只读,有界)。
- **删除**:`DetachFile` 命令 → 软删(status=DELETED);blob GC 留后续(本期不物理删,避免去重共享误删)。
- 备选:单步 multipart 直接建行——把二进制和元数据写耦合进一个事务、命令日志夹带大字节,否。

### D4 校验与有界(AG-202/203)
- 单文件 ≤ `MAX_ATTACHMENT_BYTES`(建议 50 MB,配置)、单对象附件数 ≤ `MAX_PER_OBJECT`(建议 50);
- `content_type` 白名单(建议:pdf、常见图片、office、csv/txt、zip——**闭单**,AG-405);
- `sha256` 服务端重算比对(防 client 伪报);
- 命令侧校验 storageKey 真存在(防悬空引用)。

### D5 留痕 / provenance
- `AttachFile`/`DetachFile` 进 outbox → 出现在对象的操作时间线;
- 对象详情/provenance 抽屉里"附件"区列出 ACTIVE 附件(UI 卡对接,本设计只保证读视图可查)。

## 4. 分期落地(确认后开卡)

- **Phase 1(MVP,1–2 卡)**:`StorageBackend` SPI + 文件系统实现;`attachment` 表 + 迁移 + 投影;`POST blob` + `AttachFile`/`DetachFile` 命令 + 下载 + 列表读视图;e2e:纯 API 建对象 → 传 blob → AttachFile → 列表查到 → 下载校验 sha256 → DetachFile 软删;有界/类型白名单/sha256 校验。**Docker e2e,与其它 server e2e 错峰。**
- **Phase 2(后续)**:S3/MinIO 后端实现(挂同 SPI)、blob GC、去重共享计数、对象 provenance 区接 UI。

## 5. 决策(已定稿 —— 2026-06,产品负责人批准"按推荐")

1. **blob 后端**:Phase 1 **只做文件系统**(`StorageBackend` SPI + 文件系统实现);S3/MinIO 押 Phase 2,挂同一 SPI。
2. **大小/类型上限**:单文件 **≤ 50 MB**、单对象 **≤ 50 个**;`content_type` 白名单(pdf / png·jpg·gif·svg·webp / office docx·xlsx·pptx / csv·txt / zip)——闭单,AG-405。
3. **`scopeRef` 粒度**:`scope_ref` 列从一开始就建(nullable),**Phase 1 只验对象级**(`object_id` 必填、`scope_ref` 留空);评分项级(`score:<code>`)等比选 UI 落地时再启用,**无需再迁移**。
4. **删除语义**:**软删**(`DetachFile` → status=DELETED,保留留痕);物理删 + blob GC 押 Phase 2。
5. **去重**:blob key = 内容寻址(sha256 分桶),**落盘天然去重**;但**不做引用计数**,软删只改 attachment 行、不碰 blob(避免共享误删)。引用计数/GC 押 Phase 2。

# ADR-004 关系网络存储:独立图数据库 vs 关系表+索引

- 状态:已采纳(有争议项,先列推理过程)
- 日期:2026-06-12
- 关联章节:3.5(关系是一级数据对象)、3.7(基础支撑层"图数据库或关系网络存储")、8.3(大型 50 万关系)、8.10/8.11(关系创建 P95≤500ms;关系查询必须有索引、方向与范围控制)、9.6

## 背景

本平台中"关系不是图上的线",而是可创建、查询、编辑、检查、评审、版本管理、输出交换的独立数据对象。说明书 3.7 把"图数据库或关系网络存储"列为待决项,附录E 倾向关系表方案。此处给出明确裁决。

## 推理过程(先于结论)

**第一步:刻画真实查询负载。** 逐条对照说明书,平台对关系的操作是:

| 操作                                        | 来源章节 | 图特征                                                       |
| ------------------------------------------- | -------- | ------------------------------------------------------------ |
| 创建/编辑/废止关系,带版本、状态、来源、审计 | 3.5、4.x | 这是 **OLTP 记录管理**,不是图遍历                            |
| 图形视图渲染某范围内节点+边                 | 8.4      | 按 workspace+范围取子图,**1 跳邻接**                         |
| 关系完整性/引用有效性检查                   | 8.5      | 增量异步,按依赖图算受影响范围,**1–2 跳**                     |
| 追溯/影响分析(需求→功能→接口→构件)          | 第5章    | 有限深度路径查询,典型 **≤3–5 跳**,且方向已知                 |
| 矩阵视图(行列交叉关系)                      | 6.12     | 本质是 **关系表的二维投影**,SQL 聚合最自然                   |
| 关系作为输出快照/制品交换的一部分           | 5.9      | 批量导出,扫描型                                              |
| 跨项目资产网络分析、组织级知识图谱          | 5.10     | 真正的图分析(中心度、社区发现),**唯一图原生负载,且是冷路径** |

结论:90% 以上负载是"带丰富业务属性的边记录管理 + 浅层遍历",真正的图算法负载只出现在资产沉淀的冷路径,且 MVP 不在范围(10.1)。

**第二步:一致性代价。** 关系与对象同为一级数据,变更必须与版本记录、event_outbox 同事务提交(第12章)。若关系主存放图库,则出现跨库双写:PG(对象+版本+Outbox)与图库(边)之间没有分布式事务,只能靠事件最终一致——而说明书把关系定义为**正式数据**,正式数据的事实源不允许最终一致。若图库只作只读副本,则它不是"存储方案"而是"索引",问题退化。

**第三步:性能红线核对。** 8.10 要求关系创建 P95≤500ms(含事务+Outbox);8.11 要求"关系查询必须有索引、方向与范围控制"——这句红线本身就是关系表+复合索引的设计语言。PG 在 (workspace_id, source_id, relation_type) 与 (workspace_id, target_id, relation_type) 双向复合索引下,50 万边规模的 1 跳查询是毫秒级;3–5 跳的递归 CTE 限定 workspace 范围内也完全可控。图库的优势(免索引邻接,index-free adjacency)要在**无界深度遍历、十亿边**规模才有决定性收益,本平台 8.3 的上限远未触及。

**第四步:E1/E2 代价。** Neo4j Community 为 GPLv3 且阉割(无热备/无细粒度权限),Enterprise 商业授权且对私有化保密环境授权流程复杂;JanusGraph 需再拖一套存储后端+索引后端,运维面爆炸;TuGraph/NebulaGraph 国产且有 arm64,但意味着多一套有状态中间件的离线镜像、备份、HA、升级与人才要求。E2 环境每多一个有状态组件,交付成本都是实打实的。

**第五步:反方观点(steelman)。** 支持图库的最强论点是:(a) 若未来组织级知识图谱成为核心卖点,届时迁移成本高;(b) 深层追溯(如 10 跳影响传播)递归 CTE 会退化。回应:(a) 图分析负载是冷路径只读负载,可由事件流投影出一个**衍生图副本**,不需要迁移事实源;(b) 用闭包表/路径表把高频深遍历预计算掉,正是附录E"闭包表/路径表"的用意。

## 决策

**裁决:MVP 及第一、二阶段,关系网络一律存 PostgreSQL 关系表 + 双向复合索引 + 层级关系闭包表;不引入独立图数据库。** 图数据库定位为**未来冷路径分析的衍生只读投影**,由 event_outbox 事件流异步构建,届时候选 TuGraph/NebulaGraph(国产、arm64),Neo4j 因许可证不作首选。

具体设计:

- relation 表:id、workspace_id、relation_type、source_id、target_id、direction、status、version、来源、created_by/updated_by;
- 索引:(workspace_id, source_id, relation_type)、(workspace_id, target_id, relation_type)、(workspace_id, relation_type) 三组;
- 树状/分解类关系维护闭包表(ancestor, descendant, depth),写时同事务维护;
- 深度 >5 或全空间遍历的查询禁止进入热路径,任务化执行(8.9);
- 重新评估触发条件(写入 ADR 变更记录):单空间边数 >500 万、或 ≥4 跳在线查询成为高频业务、或图算法(中心度/社区)成为正式功能。

## 风险与缓解

| 风险                                     | 缓解                                                                          |
| ---------------------------------------- | ----------------------------------------------------------------------------- |
| 深层图查询(递归 CTE)在异常数据(环)下失控 | 关系写入时由规则引擎做环检测(强语义关系);CTE 强制 depth 上限与 workspace 过滤 |
| 闭包表写放大(大子树挂接)                 | 挂接大子树走温路径异步重建闭包,期间标记"层级索引重建中"                       |
| 未来真需要图库时投影链路缺失             | 现在就保证所有关系变更经 event_outbox 发布,投影器届时只是新增订阅方,零侵入    |
| 团队把关系查询写成无索引全表扫           | 8.11 红线落地为代码评审 checklist + 慢查询监控告警                            |

## 标准对齐声明(V3.3)

- 涉及标准/事实标准:RDF/OWL/SHACL 的语义关系与图结构校验思想。
- 采用等级:B/C(语义对齐/后续扩展参考),不作为 MVP 主流程强依赖。
- 边界:关系继续作为 PostgreSQL 中的一等事实对象;知识图谱与大规模语义推理仅可作为后续冷路径只读投影。

# ADR-007 任务队列与事件投递(含 Outbox 实现方式)

- 状态:已采纳
- 日期:2026-06-12
- 关联章节:第4章(event_outbox、task_queue 表)、8.9(热/温/冷路径)、8.11 红线("所有重任务必须可排队、可取消、可重试、可缓存、可追踪")、第12章闭环(命令→主数据事务→event_outbox→可靠投递→订阅方)、9.6

## 背景

平台有两类异步负载,语义不同,不应混用一套机制:

1. **事件投递(温路径)**:主数据变更事件驱动读模型、搜索索引、规则增量检查、审计、通知。要求与主事务原子(不丢)、顺序(按聚合)、最终一致。
2. **任务执行(冷路径)**:全量检查、AI 生成、输出渲染、制品深解析、仿真、资产入库。要求优先级、进度、取消、重试、结果缓存、追踪——8.11 红线逐字要求。

## 备选方案对比

**消息中间件:**

| 维度               | RabbitMQ(推荐)                  | Kafka                                 | Redis Streams          | 仅 PG(LISTEN/NOTIFY+SKIP LOCKED) |
| ------------------ | ------------------------------- | ------------------------------------- | ---------------------- | -------------------------------- |
| 可靠投递/重试/死信 | ✅ 原生(DLX、quorum queue)      | 偏流式,重试需自建                     | 半成品(需自管 pending) | 自建                             |
| 顺序保证           | 按队列;按聚合需一致性哈希交换器 | 按分区强                              | 按 stream              | 按查询序                         |
| 运维重量(E2 离线)  | 中(单组件,Erlang)               | 重(broker 集群+协调,小规格私有化过重) | 轻(复用缓存)           | 零新增                           |
| arm64 官方镜像     | ✅                              | ✅                                    | ✅                     | ✅                               |
| 大流量事件流扩展   | 中                              | 强                                    | 中                     | 弱                               |

**Outbox 投递器(Relay)实现:**

| 方式                                                                                                                                                            | 评估                                                                                                                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **轮询发布器(Polling Publisher,推荐)**:投递器以 `FOR UPDATE SKIP LOCKED` 批量取 status=PENDING 的 outbox 行→发 RabbitMQ→确认后置 PUBLISHED,失败递增 retry_count | 实现简单、纯 SQL、无新增组件;延迟亚秒级(轮询 200ms~1s),完全满足温路径"允许最终一致"(8.9);outbox 表结构与第4章定义逐字段吻合(status/retry_count/published_at) |
| CDC(Debezium 读 WAL)                                                                                                                                            | 延迟更低、零轮询,但引入 Kafka Connect/Debezium Server 整套组件,E2 离线交付与运维成本不成比例;**否决**                                                        |
| 事务内直发 MQ(双写)                                                                                                                                             | 破坏原子性,违反第12章闭环;**否决**                                                                                                                           |

## 决策

**事件投递:PostgreSQL `event_outbox` 表(与主数据同事务写入)+ 轮询发布器投递至 RabbitMQ(quorum queue);消费者一律幂等(按 event id 去重表)。
任务执行:`task_queue` 表为任务事实源(状态机:PENDING→RUNNING→SUCCEEDED/FAILED/CANCELLED,含 priority/retry_count/started_at/finished_at),RabbitMQ 作为派发通道,worker(Java 进程,见 ADR-001)消费执行;取消与进度回写 task_queue,前端订阅任务事件。
Redis 仅作缓存与轻量协调(视图缓存、分布式锁、限流),不承担可靠投递。** 与附录E ADR-007 一致(Kafka 留作未来大型事件流的演进项)。

补充约定:LISTEN/NOTIFY 仅用于唤醒轮询器降低延迟,不作为投递通道;按 aggregate_id 哈希路由保证同聚合事件顺序;死信队列 + 告警,毒消息进隔离表人工处置;输出/深解析结果按(文件哈希+解析器版本+配置)缓存(8.11)。

## E1/E2 符合性逐项核对

| 检查项            | 结论                                                                                                                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| arm64 官方二进制? | ✅ rabbitmq 官方镜像多架构(Erlang/OTP 官方支持 aarch64);redis 官方镜像多架构;轮询器为自研 Java 代码                                                                                    |
| 国内镜像源可装?   | ✅ 两者均可同步私有 Registry;无运行期插件下载(rabbitmq_management 等插件镜像内置)                                                                                                      |
| 无公网硬依赖?     | ✅ 全内网;AI 类任务 worker 调用的大模型端点**必须**经环境变量配置(AI_GATEWAY_URL),支持指向内网部署模型——满足 9.6.2"AI 接口必须支持本地大模型端点",禁止 OpenAI/Anthropic 公网地址硬编码 |
| 无云托管依赖?     | ✅ 不使用 SQS/Pub-Sub/Service Bus/EventBridge                                                                                                                                          |
| Outbox 与主库同体 | ✅ 无跨库事务;E2 环境少一个故障域                                                                                                                                                      |

## 风险与缓解

| 风险                             | 缓解                                                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Outbox 表膨胀拖慢主库            | PUBLISHED 行按天分区滚动归档/清理;轮询走 (status, created_at) 部分索引                                                |
| 至少一次投递导致重复消费         | 消费侧统一幂等中间件(event id 去重表),作为框架能力而非各自实现                                                        |
| RabbitMQ 单点                    | MVP 单节点+持久化+快速重建预案;二期 3 节点 quorum queue;Outbox 保证 MQ 宕机期间事件不丢、恢复后续投                   |
| 长任务(仿真数小时)占用 MQ 消费槽 | MQ 只投"任务令牌",执行状态以 task_queue 为准;worker 心跳超时由调度器重派(检查点恢复,对应 6.x"任务队列+适配器+检查点") |
| Erlang 在国产 OS 的兼容性        | 仅以容器形态交付,不做裸机安装;镜像在麒麟 V10/UOS + 飞腾/鲲鹏实测后入介质库                                            |

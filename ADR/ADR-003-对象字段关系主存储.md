# ADR-003 对象/字段/关系的主存储

- 状态:已采纳
- 日期:2026-06-12
- 关联章节:3.5(对象与关系均为一级数据对象)、第4章(数据表:object/field/relation/version/event_outbox/task_queue/audit_log/snapshot)、8.3(大型空间 10万对象/50万关系)、8.10(写入 P95≤500ms)、9.6

## 背景

主存储是"平台事实源",承载对象、字段、关系、状态、来源、版本,并要求:

1. 变更命令在**同一事务**内写主数据 + 版本记录 + event_outbox(第12章闭环),这决定了主存储必须是强事务 ACID 库,且 Outbox 与主数据同库;
2. 元模型驱动:字段/属性由场景模板动态定义,需要半结构化存储能力;
3. 大型工作空间 10 万对象/50 万关系仍要满足热路径 P95≤500ms;
4. E1/E2:多架构镜像、离线初始化、无云托管依赖(明确排除 RDS/Aurora/Cloud SQL 等)。

## 备选方案对比

| 维度               | PostgreSQL 16(推荐)         | MySQL 8                 | openGauss/金仓/达梦(国产) | MongoDB              |
| ------------------ | --------------------------- | ----------------------- | ------------------------- | -------------------- |
| 事务与一致性       | 强,MVCC 成熟                | 强                      | 强(openGauss 为 PG 系)    | 多文档事务弱于关系库 |
| 动态字段(元模型)   | JSONB + GIN 索引,表达力最佳 | JSON 较弱               | openGauss 支持 JSONB 子集 | 原生但牺牲关系一致性 |
| 递归/图查询        | recursive CTE、lateral join | 8.0 支持 CTE,优化器较弱 | 视产品而定                | 弱                   |
| 全文检索兜底       | FTS + pg_trgm + zhparser    | 一般                    | 部分支持                  | 一般                 |
| arm64 官方镜像     | ✅ 官方多架构               | ✅                      | ✅(本就面向国产化)        | ✅(但 SSPL 许可)     |
| 许可证             | PostgreSQL License(宽松)    | GPL                     | 商业/木兰                 | SSPL(排除)           |
| 与 Outbox 同库事务 | ✅                          | ✅                      | ✅                        | 不适合               |

## 决策

**PostgreSQL 16 作为对象、字段值、关系、状态、版本、event_outbox、task_queue、审计与权限的唯一主存储。** 与附录E ADR-003 一致。

实施约定:

- 固定列(id、workspace_id、type、status、版本号、created_by/updated_by)+ JSONB 扩展字段承载元模型动态属性;高频筛选字段用表达式索引或物化列;
- 按 workspace_id 做应用层分区键,大型空间启用 PG 声明式分区,对应 8.3"超大型需分区分片";
- 读写分离用 PG 流复制 + 只读副本,温路径读模型读副本;
- 为兼容国产库替换诉求,SQL 层避免使用 openGauss 不支持的冷僻特性,DDL/DML 经统一数据服务层收口(7.1"统一数据服务层屏蔽差异")。

## E1/E2 符合性逐项核对

| 检查项            | 结论                                                                                                                        |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------- |
| arm64 官方二进制? | ✅ postgres 官方镜像提供 linux/amd64 + linux/arm64;麒麟/UOS 亦有发行版包                                                    |
| 国内镜像源可装?   | ✅ 镜像可同步至 Harbor/Nexus 私有 Registry,经 REGISTRY_PREFIX 切换;无部署期公网依赖                                         |
| 无公网硬依赖?     | ✅ 初始化用离线 SQL 脚本(附录E 已注明"保密环境需私有镜像与离线初始化脚本");扩展(pg_trgm、zhparser)随镜像打包,不在运行期下载 |
| 无云托管依赖?     | ✅ 自建容器/主机部署,不依赖 RDS 类服务                                                                                      |
| 国产库可替换性    | ⚠ 预留:openGauss 与 PG 协议高度兼容,但 JSONB/分区细节需专项验证后才可承诺                                                  |

## 风险与缓解

| 风险                             | 缓解                                                                             |
| -------------------------------- | -------------------------------------------------------------------------------- |
| JSONB 滥用导致无法约束、查询退化 | 元模型中声明"可检索字段"必须物化为列或建表达式索引;规则引擎校验字段 Schema       |
| 50 万关系下递归查询拖慢热路径    | 热路径只允许 1 跳邻接查询;深遍历入温/冷路径(见 ADR-004)                          |
| 单库成为全平台瓶颈               | 工作空间分区 + 读模型外置(搜索/视图缓存),主库只承担稳定事务(3.8"只承担稳定事务") |
| 客户强制要求国产数据库           | 数据服务层收口 SQL;立项 openGauss 兼容性测试集,作为商务选配而非默认路径          |

## 标准对齐声明(V3.3)

- 涉及标准/事实标准:SQL/PostgreSQL、JSON Schema、MOF 的 M3/M2/M1/M0 分层思想。
- 采用等级:A(直接采用/兼容)用于 PostgreSQL 与 JSON Schema 契约;MOF 分层仅为 B(语义对齐/借鉴)。
- 边界:外部标准文件不得替代 PostgreSQL 中的统一数据事实源;不承诺完整实现 MOF。

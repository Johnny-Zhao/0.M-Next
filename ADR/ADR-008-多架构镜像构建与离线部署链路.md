# ADR-008 多架构(amd64+arm64)镜像构建与离线部署链路

- 状态:已采纳
- 日期:2026-06-12
- 关联章节:9.6.1(linux/amd64+linux/arm64 多架构 OCI 镜像、docker buildx、选型检查项)、9.6.2(包管离线化、REGISTRY_PREFIX、运行时无外网调用)

## 背景

E1 要求所有服务镜像同时支持 linux/amd64 与 linux/arm64(飞腾/鲲鹏 + 麒麟 V10/统信 UOS);E2 要求部署全程不触公网:不访问 hub.docker.com/npmjs.com/pypi.org,镜像源经 REGISTRY_PREFIX 切换,可完整离线打包。这是贯穿 ADR-001~007 所有组件的横切决策。

## 备选方案对比

**构建方式:**

| 维度     | Buildx + 原生双架构 Runner(推荐)         | Buildx + QEMU 仿真                  | 手工分别构建+手拼 manifest |
| -------- | ---------------------------------------- | ----------------------------------- | -------------------------- |
| 构建速度 | 快(各跑各的原生)                         | arm64 侧慢 5–20 倍,JVM/前端构建尤甚 | 快但易错                   |
| 正确性   | 高(避免 QEMU 下 native 编译的隐性差异)   | JIT/紧缩指令偶发问题                | 人为失误风险               |
| CI 成本  | 需一台 arm64 构建机(鲲鹏/飞腾云主机即可) | 零额外硬件                          | 低                         |

**离线分发:**

| 方式                                                    | 评估                                                                                                                      |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **私有 Registry(Harbor)+ skopeo 同步 + 离线介质(推荐)** | Harbor 自身有 arm64 部署方案,支持多架构 manifest、镜像签名、漏洞扫描;skopeo `copy --all` 保留 manifest list 完整导出/导入 |
| docker save/load tar 包                                 | 作为无 Registry 客户的兜底通道保留;注意 `--platform` 指定,避免只打包单架构层                                              |
| 依赖客户内网代通道                                      | 不可控,仅作可选加速,不作为链路依赖                                                                                        |

## 决策

**构建:Docker Buildx 多平台构建,amd64 与 arm64 各用原生 Runner 并行构建后合并 manifest list(`--platform linux/amd64,linux/arm64`);QEMU 仅用于本地开发验证。
基础镜像:统一收口到内部基线镜像清单(eclipse-temurin:21-jre、nginx、postgres:16、opensearch、rabbitmq、redis、minio),全部 FROM `${REGISTRY_PREFIX}/...`,由 .env 切换公司 Harbor/客户内网 Registry/国内镜像源。
制品离线化:Maven 依赖入 Nexus 私服并可导出 bundle;npm 依赖经 npmmirror 同步入私服,pnpm lockfile 锁定;OpenSearch 分词插件、字体、地图瓦片、模型词典等运行期资源一律打入镜像或随介质分发。
交付介质 = 多架构镜像包(skopeo 导出)+ Harbor 离线安装包 + docker-compose/Helm 编排(全部镜像引用走 REGISTRY_PREFIX)+ 离线初始化脚本(DB Schema、桶、索引模板、词典)+ SBOM 与校验和清单。**

**依赖准入门禁(CI 强制,落实 9.6.1/9.6.2 选型检查项):**

1. 新增 Maven/npm 依赖含 native 产物时,必须存在 linux-arm64 构件,否则 CI 拒绝;
2. lockfile 全量依赖必须可从内网私服解析(断网构建作为每日流水线);
3. 镜像与代码扫描:禁止硬编码公网 URL(AI 端点、遥测、版本检查、CDN);AI 接口地址仅允许来自环境变量;
4. 每次发版在 amd64 与 arm64 双环境跑同一套 E2E(含麒麟 V10/UOS 实机定期回归)。

## E1/E2 符合性逐项核对

| 检查项            | 结论                                                                                                                                                 |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| arm64 官方二进制? | ✅ 全部基线镜像(temurin/nginx/postgres/opensearch/rabbitmq/redis/minio/harbor)经核查均有官方或官方仓库内 linux/arm64 版本;自研镜像由本链路产出双架构 |
| 国内镜像源可装?   | ✅ 基础镜像可经国内镜像站/私有 Harbor 同步;npm/pip/maven 均有国内镜像与私服方案;REGISTRY_PREFIX 写入所有 compose/Helm                                |
| 无公网硬依赖?     | ✅ 断网构建流水线 + 镜像外呼扫描双保险;运行期零外呼经网络策略(默认拒绝出站)在交付环境强制                                                            |
| 无云托管依赖?     | ✅ 构建链(GitLab/Jenkins + Runner + Harbor + Nexus)全自建,不依赖 ECR/GCR/ACR 及云构建服务                                                            |
| AI 端点可配置?    | ✅ 准入门禁第 3 条以静态扫描方式强制                                                                                                                 |

## 风险与缓解

| 风险                                          | 缓解                                                                                               |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 个别传递依赖无 arm64 产物,临近交付才暴露      | 准入门禁前置到 PR 阶段;维护"已知无 arm64 依赖黑名单";9.6.1 风险原文即此,以 CI 自动化兑现"提前发现" |
| 双架构镜像与离线介质制作流程繁琐、易漏        | 发布流水线一键产出介质(镜像导出、校验和、清单、SBOM 自动生成);介质安装演练纳入每个里程碑验收       |
| 客户内网 Registry 形态各异(Harbor/Nexus/自研) | 仅依赖 OCI 标准行为;交付前提供镜像兼容性自检脚本                                                   |
| 麒麟/UOS 内核或 glibc 差异导致容器运行异常    | 维护国产 OS 兼容性测试矩阵(OS×CPU×组件),每版本回归;优先选静态编译(Go)或 JVM 类组件,减少 glibc 耦合 |
| 国产 GPU/加速卡(AI 本地模型)架构差异          | 大模型推理服务不在平台镜像范围内,以"内网端点"解耦(9.6.2),由模型侧独立适配                          |

## 标准对齐声明(V3.3)

- 涉及标准/事实标准:OCI Image/Distribution、SBOM、OpenAPI/AsyncAPI 等可离线发布契约。
- 采用等级:A(直接采用/兼容)用于 OCI 多架构镜像与离线交付接口;其余标准文档发布为实现期 A/B 对齐项。
- 边界:C 级标准或工具不得进入 MVP 构建与运行强依赖;任何引入须先通过 ADR-009 与本 ADR 的 arm64、离线、许可准入。
